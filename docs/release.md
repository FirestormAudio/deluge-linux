# Release: the bundle, CI, and app builds

What app builds (libdeluge, deluge-sdk) depend on is the artifact this repo
publishes, not its source. If you're building an app, this page and
[docs/drivers.md](drivers.md) are the whole contract; you don't need anything
else in `docs/`.

## The base bundle

`make bundle` (or the tag-triggered CI job) assembles everything an app
needs to cross-compile and boot, without ever running Buildroot itself:

```
deluge-base-<version>/
├── boot/
│   ├── base/            u-boot.bin, r7s72102-deluge.dtb, zImage — this profile's kernel
│   └── platform/        u-boot.bin, r7s72102-deluge.dtb, zImage — this profile's kernel
├── rootfs/
│   ├── base.cpio       the appliance profile's rootfs
│   └── platform.cpio   the hackable profile's rootfs
├── toolchain/          relocatable cross-toolchain + sysroot (from `make sdk`)
├── tools/
│   ├── deluge-mkimage  the packer's entry point (a shim; see below)
│   ├── deluge_mkimage/ the packer itself, a Python package
│   ├── memmap.py       memory-map loader the packer imports
│   └── uimage.py       U-Boot legacy header writer the packer imports
├── manifest.json       the load-address map (same file as memory-map.json)
└── DelugeToolchain.cmake
```

Each profile ships its own kernel as well as its own rootfs: `platform`'s
kernel has networking, `base`'s does not. U-Boot and the DTB are the same for
both profiles (and the toolchain is shared), but `scripts/mk-bundle.sh` copies
them into every `boot/<profile>/` so that each directory is self-contained: the
packer reads every segment file from one directory, and
`Bundle.boot(profile)` points at exactly one. `mk-bundle.sh` fails if the two
DTBs ever differ.

`mk-bundle.sh` builds the profiles one after the other. Before each one it
wipes `.buildroot/output/target` and the per-package install stamps, because
Buildroot's target tree is incremental and never removes files; without the
wipe, `platform.cpio` would also contain `base`'s files. Packages are
reinstalled, not recompiled.

## `manifest.json`

The same file as `board/synthstrom/deluge/memory-map.json`. It carries the load
address for every segment in the app-loader ELF, keyed by filename. The real
file also has a `"comment"` field explaining the map's purpose and its
cross-dependency with U-Boot's bootcmd, omitted here for brevity.

```json
{
  "version": "0.2.0",
  "segments": [
    { "file": "u-boot.bin", "load": "0x0C000000" },
    { "file": "r7s72102-deluge.dtb", "load": "0x0DF00000" },
    { "file": "zImage", "load": "0x0E000000" },
    { "file": "rootfs.uimg", "load": "0x0E800000", "max_size": "0x1000000", "generated": true }
  ]
}
```

`generated` marks the one segment the packer doesn't read straight off disk:
the rootfs, which gets wrapped in a U-Boot legacy image header at pack time.
Packing an ELF from the bundle means pointing the packer at one profile's
`boot/<profile>/` and the matching `rootfs/<profile>.cpio`. From a checkout of
this repo:

```sh
python3 tools/mk-app-elf.py --map manifest.json --dir boot/base/ \
    --rootfs rootfs/base.cpio out/LINUX.ELF
```

`release.yml` does exactly this for both profiles, and `deluge-mkimage` (below)
does the same with the app baked into the rootfs first. See
[docs/boot.md](boot.md#memory-map) for what these addresses mean.

## `DelugeToolchain.cmake`

A CMake toolchain file, generated by `scripts/mk-bundle.sh` and shipped at the
bundle root. Point an app's build at it:

```sh
cmake -DCMAKE_TOOLCHAIN_FILE=$DELUGE_BASE/DelugeToolchain.cmake ...
```

It's relocatable: every path it sets derives from
`CMAKE_CURRENT_LIST_DIR`, wherever the extracted bundle ends up on disk,
rather than the path the toolchain was built at. That matters because
Buildroot's SDK bakes its build-host path into the toolchain's linker scripts,
`.la` files, and wrapper scripts; `mk-bundle.sh` runs the SDK's own
`relocate-sdk.sh` against the extracted `toolchain/` directory before
generating this file, specifically so the bundle works on a machine that never
built it.

It also sets `PKG_CONFIG_LIBDIR` to the sysroot's `pkgconfig` directory.
Without that, `pkg_check_modules(ALSA)` silently resolves against the *host's*
ALSA and links an app against x86 headers, a bug with no build-time error that
only fails at runtime, on the board.

## Packing with `deluge-mkimage`

`deluge-mkimage` ships in the bundle's `tools/` so app builds can pack images
without cloning this repo. `tools/deluge-mkimage` is a small shim: it puts its
own directory on Python's import path and runs `deluge_mkimage.cli`. The code
is the `tools/deluge_mkimage/` package, which imports `memmap.py` and
`uimage.py` from the same directory. Run it as
`$DELUGE_BASE/tools/deluge-mkimage <app> [options]`; `--help` lists the
options.

It takes a compiled app, validates it, and produces either of two products
from one compile: an appliance image for the card's `/APPS/` (the app baked
into the profile's rootfs and packed into a `LINUX.ELF`-style ELF), or, with
`--bare`, the validated binary alone for the card's `/LINUX/APPS/`.

`--dynamic` permits a dynamically linked app, verifying the app's own
`DT_NEEDED` closure and each staged prefix library's own closure against
the rootfs being packed. `--prefix <dir>` supplies the app's private `$ORIGIN`
libraries, implies `--dynamic`, and — for the image product — is baked into
the packed cpio at `usr/lib/<name>/` (where `<name>` is `<dir>`'s own
basename), the same place `$ORIGIN/../lib/<name>` resolves to once the app is
running at `/usr/bin/deluge-app`. The bare product ships no prefix of its own;
it relies on the prefix directory being copied alongside it onto the card, at
`/LINUX/lib/<name>/`. libdeluge's CMake helper, `deluge_add_app()`, lays the
card out that way.

This verifies libraries, not symbols: it proves every name in the
`DT_NEEDED` graph, and the interpreter, is present and resolvable, not that
every symbol referenced across those libraries actually resolves. Symbols are
not checked.

## What CI publishes

Two workflows, two different jobs:

- `build.yml` runs on every push to `main` and every PR, as two independent
  jobs: `tools` (the pytest suite, which fails in seconds if the packing tools
  are broken) and `build` (both profiles, uploading `LINUX.ELF` plus the raw
  kernel/U-Boot/DTB as short-lived CI artifacts). They run concurrently, and a
  failing `tools` job does not cancel or block `build`; it just surfaces the
  packer failure quickly alongside whichever profile builds finish. Neither
  touches the bundle.
- `release.yml` runs on every tag push (`v*`). It runs the same pytest suite
  first and only builds if that passes, so a broken packer can't spend hours
  building and then publish a bundle nobody can unpack. Then it runs `make
  bundle VERSION=<tag-without-v>`, packs `LINUX-base.ELF` and
  `LINUX-platform.ELF` from each profile's `boot/<profile>/` and cpio in the
  bundle without a rebuild, validates both with `tools/check-app-elf.py`, and
  publishes `deluge-base-<version>.tar.zst` plus its `.sha256` and both ELFs as
  a GitHub release.

Only tags produce a bundle. A plain push to `main` never does. If you need a
bundle to test libdeluge or deluge-sdk changes against, tag a release (or run `make bundle`
locally).

## Consuming a release

Consumers should pin a specific bundle by version and checksum rather than
tracking `main`:

```
version: 0.1.0
sha256:  <the .sha256 file's contents>
```

`scripts/mk-bundle.sh` prints exactly this pair at the end of a local build, so
copying its output into the consumer's pin is the whole update procedure.
